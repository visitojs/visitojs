# Decisions

How the ids of version 3 are built, and the evidence for each choice. Version 3 is the definition 1.0.0 ships; what it changed from version 2 is under [Id definition, version 3](#id-definition-version-3).

Most of the evidence is one phone session on 12 November 2026: 35 visits to a test page that ran every candidate read, 33 from three devices and two from an automated scanner (see Flags). The devices were a Pixel 10 (Chrome, Chrome incognito, Brave, Brave private, the in-app browsers of Instagram and Facebook), an iPhone 14 Pro (Safari, Safari private, Chrome, Instagram's in-app browser) and a Windows PC (Chrome, Brave). Three devices show what stays the same on one device across browsers. They cannot show how well a value separates many devices. Where a choice rests on published research or on a vendor's documentation instead, the entry says so.

## Id definition, version 3

Decided 13 November 2026. `ID_VERSION` goes from 2 to 3 once, for every change to what `id` and `idStrict` are built from since 0.1.0 (owner decision O8: one raise before 1.0, so 1.0.0 ships a definition meant to last through an LTS). Every `id` and `idStrict` changes once at this version, for every visitor, because the version is in the hashed text. The stored id (`did`), its cookie and localStorage entry do not change. The cache is keyed on the version, so a cache entry written by a version-2 build is not replayed. The matcher is unchanged: a stored reading of another version is compared by stored id only (decisions R6 and R16 in the workspace roadmap).

No value enters an id here that version 2 did not have. Each change below either corrects how a part already in an id is derived, excludes a value a browser documents as altered, or records a change made since 0.1.0 that never raised the version.

### How a server recomputes both ids from `c`

`c` holds the final parts, so nothing has to be re-derived:

1. Take every key of `c` that starts with `hw.` or `p.`.
2. Write each as `key=String(value)`, a carriage return or line feed in a value replaced by a space, sort the lines by key and join them with a line feed.
3. `id` is the lowercase hex SHA-256 of the UTF-8 text `visito:3`, a line feed, then those lines.
4. `idStrict` is the same with four more lines, all of them sorted by key together with the parts above: `v.os` (the reading's `osVer`), `v.app` (`app`), `v.appVer` (`appVer`) and `v.engine` (`engineVer`). `v.os`, `v.appVer` and `v.engine` are `!na` when the field is null or an empty string, and `v.engine` also when it is 0 (the code writes `field || '!na'`); `v.app` is always the label itself. There is no `idStrict` without an `id`.
5. Neither id exists when any `hw.` or `p.` value is `!err` or `!to`, or when `x.id` is `!err`.

Which parts appear, and when one is `!ex`, by the engine the feature tests found (`x.engine`; the Safari 17, Firefox 143 and Brave answers have no key of their own in the product build, only their `!ex`):

| Part | Present | Value | `!ex` when |
|---|---|---|---|
| `hw.model` | always | The model from the user agent's Android tokens (skipping `wv`, `U`, `Mobile`, `Tablet`, `rv:...`, a locale and, from version 3, `HarmonyOS`; from version 3 an `HMSCore` token right after `HarmonyOS` means no model), an iPhone's `iPhoneN,M`, Instagram's suffix, or client hints when the user agent says `K`; `!na` when none names one | never |
| `hw.mem` | always | `deviceMemory` as 2 (below 4), 4 (below 8) or 8; `!na` where it is not exposed (WebKit, Gecko) | Brave, any engine |
| `p.lang` | always | `navigator.language` | never |
| `p.txt` | always | WebKit: the computed size of `font: -apple-system-body` (Dynamic Type). Elsewhere: `env(preferred-text-scale)` when it reads other than 1, else the computed size of a fixed 100px font, rounded to a whole pixel, divided by 100. On an engine without `env()` the scale is `!na` and the fixed font decides (version 3; before, the scale probe took the page's own line height there). A failed read of the value that decides is `!err` or `!to`, never replaced by the next one (version 3) | never |
| `hw.scr` | only when `hw.model` is `!na` | `screen.width` and `height`, longer side first, as `852x393` | WebKit at the Safari 17 level (every WebKit browser on iOS and iPadOS 17 and later, Safari or not, and WebKit browsers and web views on macOS at that level); Gecko at the Firefox 143 level; Brave that is not an Android build (version 3) |
| `hw.cores` | only when `hw.model` is `!na` | `hardwareConcurrency` | Brave, any engine; Gecko at the Firefox 143 level |

So, per engine as the feature tests see it: Blink (Chrome, Edge, Opera, Samsung Internet, Android web views) has everything; Brave's Android build has memory and cores excluded, its desktop builds memory, cores and screen; WebKit below the Safari 17 level has no memory value and keeps screen and cores; WebKit at that level has the screen excluded; Gecko below 143 has no memory value and keeps screen and cores; Gecko at 143 and later has screen and cores excluded; `other` (EdgeHTML, Internet Explorer, a window whose tests contradict each other) has nothing excluded and no WebKit text style.

### What changed from version 2

Changed in this version:

1. **Brave's desktop builds leave the screen out.** Brave's farbling test page (dev-pages.brave.software/fingerprinting/farbling.html, read 13 November 2026) lists "Screen resolution" and "Available screen resolution" as altered at both Shields levels, and brave-core's `kBraveBlockScreenFingerprinting` is on by default on Windows, macOS and Linux ("Five small reads" below). Lab observation on this PC, 13 November 2026, the installed Brave 1.99.57 (Chromium 157.0.8103.79) with a fresh profile per launch, on a 1920x1080 display: `screen` read 1280x800 with windows of 1200x800 and 900x700 and 1680x1050 with one of 1500x950; Playwright's Chromium 153 read 1920x1080 in all three. One device's id would split with the window size. The same runs read cores 14, 10 and 10 (16 logical processors) and memory 8, 32 and 32, which the existing exclusions already cover. Brave's Android build keeps the screen: the page names no platform, and on the Pixel 10 Brave's screen read the same as Chrome's in normal and private windows. What is left of the id on Brave's desktop builds is the language and the text size, with `flags.weak` true: every Brave desktop with the same language and text size shares one `id`, and only the stored id tells them apart. Code: `exclusions()` in `src/stages.ts`, `scr: ... || (env.brave && !env.android)`.
2. **A failed text read no longer falls through to another one.** Version 2 skipped any status in `x.txt.apple` or `x.txt.env` and let the next value decide: on Chrome a failed scale read gave `p.txt = 1` from the fixed font whatever the user's setting, on WebKit a failed system-style read gave the scale or the fixed font, and an unreadable fixed font gave `!na`, each hashed into an id with `flags.partial` empty. Now `!err` or `!to` in the value that decides becomes `p.txt` (no id, `p.txt` named in `flags.partial`), a fixed font with no number is `!err`, and on WebKit a system text size that is not a number is `!err` instead of `!na`. Only a page that breaks `getComputedStyle` or the probe can reach these cases; what an intact browser reads gives the value it gave before. `!na` is still skipped where a browser lacks the source: `x.txt.apple` outside WebKit, `x.txt.env` without `env()`. Code: `textScale()` in `src/reading.ts`, `textSize()` in `src/probes.ts`.
3. **On an engine without `env()` the scale is `!na` and no longer follows the page.** MDN browser-compat-data (`css.types.env`, read 13 November 2026) gives `env()` from Chrome 69 (Chrome for Android, Android WebView, Samsung Internet and Opera on the same Chromium), Firefox 65 and Safari 11.1. An engine before those drops the declaration `line-height: calc(env(preferred-text-scale, 1) * 100px)`, so in version 2 the probe span kept the line height it inherits from the page: on a page with `body { line-height: 1.5 }` and 16px text `x.txt.env` read 0.24, which is not 1, so it became `p.txt`, and one device got a different id on each site. The probe now declares `line-height: normal` first and the `calc(env(...))` line second: an engine with `env()` takes the second, so its value is unchanged, and one without it keeps `normal`, which reads as no number, `!na`, and the fixed font decides. Code: `textSize()` in `src/probes.ts`.
4. **`HarmonyOS` is not a model.** Huawei's browser on the Android-based HarmonyOS writes the system's name among the Android tokens, before the model, so version 2 hashed `hw.model = HarmonyOS` for every such phone: different models shared it, and the phone's other browsers, which send the model, gave another id. Huawei publishes no user agent for that browser; the shape is from a third-party sample (juejin.cn/post/7429243711807471668, `Linux; Android 12; HarmonyOS; NAM-AL00; HMSCore 6.14.0.302 ... HuaweiBrowser/15.0.7.301`, read 13 November 2026) and a news report that Huawei replaced "Android" with "HarmonyOS" in the browser's user-agent setting (huaweicentral.com, secondary). Huawei's own ArkWeb template for HarmonyOS NEXT (developer.huawei.com, "Default User Agent", read 13 November 2026) has no Android token and no model, and still parses as `os: other` with no model. A token exactly `HarmonyOS` is now skipped and the next one is the model. The shape is unverified: no Huawei document and no device here confirm where the model sits or that it is always there. So a token that starts with `HMSCore` right after `HarmonyOS` is taken as no model rather than as one: it names Huawei's mobile services with their version, which changes with every update of those services, and hashing it would split one phone's ids at each update. Such a phone is then weak, as one with no model is. Code: `parseUa()` in `src/ua.ts`. Tests use synthetic strings of that shape.
5. **Opera on iOS is `opera`.** Opera documents no iOS user agent (help.opera.com/en/mobileios, read 13 November 2026); the one dated string (appdevelopermagazine.com, 2014) carries `OPiOS/` and no `Version/`, which version 2 labelled `webview`, and `safari` when a `Version/` is present. `OPiOS/` now gives `app: opera` with its version. This changes `idStrict` only (`v.app`, `v.appVer`); `id` has no app. Code: the `APPS` table in `src/ua.ts`.

Changed between 0.1.0 and this version without raising it, found by comparing how each part and each exclusion is computed at `v0.1.0` (commit `3cc4549`) and on the branch this version is built on:

6. **The Safari 17 screen exclusion covers every WebKit browser at that level** (decision 5 under "Engine detection", workspace decision R17). 0.1.0 set it for Safari itself only, through a check on `window.browser` and `print`, and with five other feature tests. On iPhone and iPad from iOS 17, Chrome, Firefox, Edge and in-app browsers that name no model lose the screen from their id, and so do WebKit browsers and apps' web views on macOS at that level. Playwright's WebKit 26.6 for Windows now counts as Safari 17 too (a lab build, not a visitor's browser).
7. **The engine is told by other feature tests** ("Engine detection" below). The engine decides the exclusions and whether the WebKit text style is read, which is `p.txt` there. Measured the same as 0.1.0 in Chromium 153, Firefox 155 and WebKit 26.6 here, except the Safari 17 answer of item 6; Chrome 53 to 80 read as Blink with nothing excluded under the new tests in CI, where 0.1.0 was not run for comparison. Not compared: Safari on Apple devices, old Safari and iOS, WebKitGTK and WPE (which now read as `other`: no WebKit text style, no screen exclusion; see "Known limits").
8. **The Firefox 143 answer needs two of three tests instead of three of four** (`::after::marker` dropped). The same answer in Firefox 155. On a page whose `CSS.supports` answers true to everything, Firefox 143 and later now keeps screen and cores in the id, where 0.1.0 excluded them.
9. **Brave is told in any engine, by `isBrave` being present.** 0.1.0 required Blink and a function. Brave on iOS, if it exposes the API (not established), now has memory and cores excluded; memory is `!na` on WebKit anyway, so it becomes `!ex`. Fixed in version 3: on a page whose `String.prototype.split` returns an object or an empty list, the path test's last name came out `undefined` and was looked up as `'undefined' in window`, which is true in every window, so the page read as Brave and lost memory, cores and, with item 1, the screen; the last name must now be a string, and such a page gets the answer that excludes nothing, as when `split` throws (`holds()` in `src/env.ts`).
10. **A screen side that is not a finite number gives `!na`.** 0.1.0 wrote an infinite side out (`Infinityx393`). No browser reports one.
11. **Hostile pages.** On pages that break `Object.prototype.hasOwnProperty`, `Function.prototype.call` or `Object.prototype` (the text probe), or throw from a client-hint brand, the code of 0.1.0 threw inside the read and gave `!err` and no id; the code since reads the value, so such pages now get an id. The size work measured these under `lab/equivalence.mjs` ("Five small reads").

Unchanged since 0.1.0, checked part by part: the model parser (identical output on 1,404,596 inputs when it was shortened), the memory buckets, the language, the core count, the text probes' declarations and reads on an intact page, the canonical text and the SHA-256 output.

### Considered and left as they are

- **iPad read as a Mac.** WebKit's desktop-class user agent on iPadOS is the Mac string, byte for byte (WebKit `UserAgentIOS.mm` and `UserAgentMac.mm`; Apple, WWDC19 session 203; WebKit bug 212937, "Please do not implement any 'Mac' vs. 'iPad' code paths"; all in `research/parser-edges-brief.md`, read 13 November 2026). No parse of the string can tell them apart. What could is `navigator.maxTouchPoints`, which WebKit returns as 5 on iOS and iPadOS and 0 on macOS; the library reads it today only inside the `no-touch` mark, and only once the user agent already says Android or iOS, and the lab build records it as `x.touch`. Using it to set `os` would make a value the id never read decide `idStrict` (`v.os` from `10.15` to the iPadOS version, or none for Chrome and a fixed `26.4` for Firefox on iPad) and the matcher's `os`. That is a new input to an id, which needs one session on a real iPad first: Safari, Chrome, Firefox and an in-app browser, recording `x.touch`, `x.plat` and the user agent. `id` itself is not affected.
- **Firefox's screen exclusion.** Mozilla's lists of protections on by default in private windows and ETP Strict (`RFPTargetsDefault.inc`) and in every window (`RFPTargetsDefaultBaseline.inc`), mozilla-firefox/firefox `main`, read 13 November 2026, contain `ScreenAvailToResolution`, `MaxTouchPointsCollapse` and, in the first only, `NavigatorHWConcurrencyTiered`; neither contains `ScreenRect`, the target that alters `screen.width` and `height`, which only `privacy.resistFingerprinting` turns on. MozillaWiki "Fingerprinting" (last edited 10 November 2026) dates the available-area and touch-point protections to private windows from 143 and every desktop window from 151 (Android: rollout from 160), and the tiered core count to private windows and ETP Strict from 143 with no every-window date. So Mozilla documents no change to the value `hw.scr` reads for ordinary users. Lab observation, Playwright's Firefox 155.0 on this PC, 13 November 2026, headed on a 1920x1080 display and headless: `screen` 1920x1080 (headless 1366x768) by default, with `privacy.fingerprintingProtection` and with `browser.privatebrowsing.autostart`; `privacy.resistFingerprinting` gave 1400x900 headed and 1200x600 headless, both following the window. The available area read 1920x1032 in every mode but `resistFingerprinting`, though the baseline list has `ScreenAvailToResolution`; why this build does not apply it was not established. The exclusion is kept: restoring the screen to Firefox ids is a promotion, which needs real Firefox on a desktop and on Android, normal, private and ETP Strict windows, across window sizes. It is not widened either: the available area and touch points are not id parts.
- **Firefox's core count.** Excluded from 143 in every window, as before. Mozilla tiers it only in private windows and ETP Strict (Mozilla's security blog, 10 November 2026: "4 or 8"); measured here, 16 logical processors read 16 in a normal window and 8 with either protection, so any form of the raw count splits one device between its windows. A tier of our own that the clamp cannot split (for example 8 for 8 or more, else the tier Mozilla gives) would put cores back into Firefox ids, a promotion that needs Mozilla's exact tier rule confirmed on real machines with 4, 6, 8 and more cores. Firefox before 143 has no clamp for ordinary users (Bugzilla 1978414 shipped it in 143); `privacy.resistFingerprinting` clamps it whatever the version, which is the user's own choice.
- **Text size on Android Chrome below 138.** Chrome 138 (stable 24 June 2025; developer.chrome.com/release-notes/138, read 13 November 2026) added the CSS environment variable that "will reflect the scale chosen by the user"; before it, the probe's `env(preferred-text-scale, 1)` reads its fallback, 1, and Chrome's computed fixed font is 100 whatever the setting, so `p.txt` is 1 there. In an in-app web view before 138 the fixed font follows the setting (the text zoom), so `p.txt` already gives the setting. The part therefore means "the user's text scale where the browser shows it, else 1", and on Chrome below 138 "1" also stands for "not shown". Excluding it there was rejected: no feature test tells Chrome 138 apart without a layout, the `env()` fallback cannot be told from a real 1, and an exclusion would change the id of every user, default size included, at the update to 138, where today only users with a non-default size see one change. Making the probe meet the layout conditions under which older Chrome applies the system font size would be a new derivation that needs an Android emulator with Chrome 137 and 138 and a web view, at two font scales. Chrome 138 is 17 months old; what is left below it is a shrinking share.
- **WebKit text probe.** Reporting `x.txt.apple` as `!na` on a WebKit build that rejects `font: -apple-system-body`, and adding `-webkit-text-size-adjust: none` as WebKit's own test does, were proposed for this version ("Five small reads"). Both move `p.txt` on WebKit and need Safari on an iPhone first; not done.
- **Brave on iOS.** Brave's iOS issue 5268 farbles `hardwareConcurrency`, which is an id part on iPhones that name no model. Whether Brave on iOS exposes `navigator.brave` is not established; if it does not, its cores stay in the id and move per session there. Needs a real iPhone.

## What `id` is built from

| Part | What it is | Evidence |
|---|---|---|
| `hw.model` | Phone model from the user agent, an in-app browser's suffix, or client hints | Present in Chrome, Instagram and Facebook on the Pixel, and in Instagram on the iPhone. The Facebook app's user agent named no model at all; client hints gave it inside that browser. Absent in Safari and Chrome on iPhone, in Brave, on desktop |
| `hw.mem` | Device memory in three buckets (2, 4, 8) | Same in Chrome, incognito, Instagram and Facebook on the Pixel. Not exposed on iPhone |
| `p.lang` | Primary language | Same in every browser of each device. The full list is not used: the in-app browser reports a shorter one than Chrome on the same phone |
| `p.txt` | The user's text-size setting | See below |
| `hw.scr`, `hw.cores` | Screen size in CSS pixels, long side first, and core count. Only when there is no model | The screen was the same in Safari, Chrome and Instagram on the iPhone, and in Chrome and Brave on the Pixel |

The id is null until every part is read. A part the browser does not have is hashed as "not available", which is a stable answer; a part that failed or timed out leaves no id, because an id from a partial set would differ from the next complete one.

### Text size

On the Pixel the font scale was set to 1.15. `env(preferred-text-scale)` reported 1.15 in Chrome, incognito, Brave, Instagram and Facebook alike. The computed size of a 100px font was 115 only inside Instagram and Facebook, where the in-app browser applies the setting as a text zoom, and 100 in Chrome. So the part is the scale where it is not 1, else the computed size divided by 100. That gives one value across Chrome, a current in-app browser, and an in-app browser older than Chromium 138, which has no `env()` value but does zoom the text.

On WebKit the part is the computed size of `-apple-system-body`, which follows Dynamic Type. It was 17 in Safari, Chrome and Instagram on the iPhone.

Reading it needs the document, so the ids are ready when the page has parsed, not at script start. The stored id is ready at script start. A reading cached from an earlier page view has both ids at script start.

## What `idStrict` adds

The parts of `id` plus OS version, app family, app version and engine version. Two phones of one model often run different app versions, so this separates them inside a short window. It changes with every update, so it must not be compared across days.

Two ideas behind these ids come from published research: linking readings by rules rather than requiring one exact hash, which the matcher does (Vastel, Laperdrix, Rudametkin and Rouvoy, 2018), and removing version numbers before comparing, which is why `id` has none (Pugliese et al., PETS 2020).

## Engine detection

`src/env.ts` was rewritten on 2026-11-12 from a behaviour specification, with every earlier implementation closed. The test list and its rules are in `docs/SIGNALS.md` ("Engine detection"). Three sets of five features vote for Blink, WebKit and Gecko, and three of five choose an engine. Every feature is in its engine for that engine's whole range and in no other engine, so two features lost or gained by accident change no engine. Features are not independent when they go through one object: no set has more than two tests behind one object or function, counting `CSS.supports` as one, so a page that breaks one of them changes no engine and no Safari 17 answer. The first version of this rewrite had three WebKit tests behind `CSS.supports`; deleting `window.CSS` or replacing `CSS.supports` turned WebKit 26.6 into `other`, kept the screen in the id, and skipped the system text-size read and the private-window check. Two outcomes of a single fault remain, both asserted by the unit tests and the fault matrix: Firefox 143 and later on a page that breaks `CSS.supports` is treated as an older Firefox there (screen and cores stay in the id), because Firefox 143 shipped nothing else a script can test by existence; and a page that breaks `navigator` loses Brave, whose own API is the only evidence of it. A CSS condition counts only when `CSS.supports` also refuses `(:)`, a declaration without a property, which no engine can accept: before that guard, a page that replaced `CSS.supports` with a function answering `true` to everything raised Firefox before 143 to the 143 level and Safari 16 with a `URL.canParse` polyfill to the Safari 17 level. Such a replacement now counts for nothing, as a broken `CSS.supports` does, so Firefox 143 and later reads as older there too.

## The in-memory-session check behind `flags.private`

Rewritten from a short behaviour specification in our own words and from these primary sources, all read on 12 November 2026:

- WHATWG File System Standard, `getDirectory()`: when the storage key cannot be obtained, the promise is rejected with `SecurityError`. WHATWG Storage Standard, "obtain a storage key": it fails when the user has disabled storage.
- MDN, `StorageManager.getDirectory()`: `SecurityError` and `UnknownError` are thrown in private browsing in some browsers. MDN, `StorageManager`: secure contexts only. `@mdn/browser-compat-data`: `getDirectory` since Safari 15.2 and Firefox 111.
- WebKit blog, "The File System API with Origin Private File System" (2022-02-14): unavailable in Private Browsing. WebKit, "Tracking Prevention in WebKit": private browsing uses ephemeral sessions. Apple, `WKWebsiteDataStore.nonPersistent()`: an in-memory store "to implement private browsing in your web view".
- Bugzilla 1785125 (file system disabled in private browsing, Firefox 109), 1875283 and 1366318 comment 13 (`SecurityError` in private windows), 1975760 (file-system support for private windows, open and in progress).
- Google, "Protecting private browsing in Chrome" (2019-07-18): Chrome closes incognito detection on purpose.

Decisions on the specification's open questions:

1. `flags.private` means "this session's storage is not kept: a private window, or an app's in-memory web view". No documented signal separates the two, and for a site both mean the stored id ends with the session.
2. Gecko: a refusal named `SecurityError`, with `localStorage` readable, gives true. A file system that opens gives `!na`, so `flags.private` is null, not false. Mozilla is landing file-system support for private windows (Bugzilla 1975760); after that release an open file system says nothing, and a build pinned in a site's pages for the life of the LTS could not be corrected. The library does not assert what it may be unable to keep true. **Behaviour change from 0.1.0**: normal Firefox windows reported `false` and now report `null`.
3. WebKit: opens gives false, `UnknownError` gives true, any other name `!na`. The weekly `browser-drift.yml` run watches both engines (see "Watched every week" under "Engine detection"); it has not run in GitHub Actions yet. Until it does, a WebKit release that opened the file system to ephemeral sessions would turn private windows into a wrong false in pinned builds, the same risk decision 2 avoids for Gecko.
4. The check still runs only when the storage is fresh, and only in WebKit and Gecko; the lab build runs it on every view. Blink stays null, and nothing is read there.
5. Whether `getDirectory()` leaves anything on disk is not established for Safari; what could be observed is below.

## The deferred build, 13 November 2026

`visitojs/defer` (`visito.defer.min.js`, `visito.defer.esm.js`) is the product build with one more call, `start(options?)`. Until the page calls it the build reads nothing and stores nothing. No id part changes, `ID_VERSION` does not change, and the stored id and the cache keep their names and format, so the two builds can be mixed on one site.

- **A separate entry, not a flag in the core.** A flag would cost every site about 100 bytes and add `start` to the core's frozen surface, and it cannot help the ES module: a static import runs before the module that imports it, so a bundled site could not set the flag before the session started. The shared change is one argument, `bare`, from `start()` in `src/stages.ts` to stage A: it gates the cookie, localStorage and the sessionStorage fallback, and the private-window task. It costs the core 21 bytes gzipped (7,349 on the branch it was built on, 7,370 with it), under the ceiling of 24 set for it, so the build-time constant that would have made it free was not needed. `open()` is unchanged; `deferred()` beside it is tree-shaken out of the core. The deferred build is 7,472 bytes, the core plus 102; its test allows the core plus 134 (measured plus 32) and 8,192 in all.
- **Nothing before `start()`, proved three ways.** Unit tests load both script-tag files and the ES module into a context whose global and window are recording proxies, so that a lookup of any name is logged, built-ins included: at load the only operation is the definition of the global `Visito`, and `getSync()` and `get()` before `start()` add none. The same harness on the core build sees its reads, so the recording works. `lab/defer.mjs` wraps every accessor and method of the browser objects the library could reach before any page script runs, in Chromium 153, Firefox 155 and WebKit 26.6: a page that loads the build and calls `getSync()` and `get()` logs nothing in 3 seconds after `load`, and leaves no cookie, no localStorage, no sessionStorage and, in Firefox, no origin usage. What a page cannot redefine (`window`, `document`, `location`, `top`) is not wrapped there; the reads behind them are on the wrapped prototypes. `lab/equivalence.mjs` shows that the deferred build started at once gives the core's outcome in every synthetic window, broken built-ins included: the same readings, callbacks, stored values and calls on the window.
- **The first `start()` decides.** Repeated events from a consent tool are then harmless, and a page view never switches between modes halfway, with a stored id that would appear or vanish within one view. A switch from `store: false` to storing can come only in a major version.
- **Ambiguous options store nothing.** Only no options, or an object whose `store` is absent or `true`, store. `false`, `0`, `'no'`, `null`, a getter that throws, `Object.prototype.store` set to `false`, and options that are not an object (`start(false)`, `start('no')`) all store nothing. A wrong guess toward storing is the failure a site cannot take back; a wrong guess toward not storing costs one view's stored id.
- **No private-window check with `store: false`.** The check opens the origin private file system, which is storage. Measured with `lab/defer.mjs` on 13 November 2026: in Firefox 155 a new visitor on the product build leaves 507,904 bytes of origin usage (`navigator.storage.estimate()`), and the deferred build before `start()` and with `store: false` leaves 0. `flags.private` is null in that mode, `x.private` absent.
- **`crypto.getRandomValues` still runs once with `store: false`.** Stage A makes a stored id before it knows none can be kept; the bytes are dropped. It is no read of the device, and skipping it would cost core bytes.
- **No `stop()` or `forget()` in 1.0.** Each would be frozen surface for what four documented lines do; `docs/LEGAL.md` has them, and `lab/defer.mjs` checks that they leave nothing in all three engines, also where reading localStorage throws and the cache is in sessionStorage. Each storage has its own `try`, so that throw does not skip the sessionStorage line.
- **Firefox's font-visibility warning is skipped, by name.** On Ubuntu 24.04 in CI, Playwright's Firefox 155 logged "Request for font "WenQuanYi Zen Hei Mono" blocked at visibility level 2 (requires 3)", and the same for "IPAGothic" and "WenQuanYi Zen Hei", on `/c-parse` and `/d` only: the two pages row (h) opens under `browser.privatebrowsing.autostart`. One was attributed to `about:blank`, the others to the build's file. Level 2 is what `ComputeFontVisibility` gives when the fingerprinting-protection target `FontVisibilityLangPack` applies, which it does in private browsing by default; elsewhere the level is the `layout.css.font-visibility` preference, 3 by default, at which no installed font is hidden. On this PC (Windows, Firefox 155) a page naming a user-installed font is warned at level 2 under `browser.privatebrowsing.autostart`, and not at all in a normal launch or with `privacy.fingerprintingProtection.pbmode` set to `false`. On Linux `gfxFcPlatformFontList::FindGenericFamilies` takes a generic family's fonts from fontconfig and reports each one hidden at the page's level; the CJK fonts `playwright install-deps` installs count as user fonts (3). The text-size read's `font-family: monospace` node, the same in the product build, is one such lookup. `x.txt.w` is measured in that family, so the read keeps it. `lab/notices.mjs` names the warning with an anchored pattern; `lab/defer.mjs` and `lab/stability.mjs` skip and count it. Row (j) of `lab/defer.mjs` opens `/c-parse` without the library (default-font text and the read's nodes written as markup) in a private launch of its own that never loads the library, in three to six fresh contexts, hears every document of each context from before its first page, and fails unless that launch is warned about every font the library's pages were. ## Five small reads, re-derived (13 November 2026)

The client-hint brand filter, the system text-style read, the screen's order, the Brave exclusions and the lab stage's start and yield were written again from a behaviour specification (`research/specs/small-reads.md` in the workspace), itself written from the primary sources below, read on 12 November 2026. None of them changes `id`, `idStrict` or any id part in a browser: run in Node against the build before it, in 36 synthetic windows, intact and under 138 broken built-ins, the readings, the stored values, every call made on the window and the built-ins called are the same on intact built-ins (`lab/equivalence.mjs`). Under broken built-ins 498 of the 19,944 runs differ and none is worse: 96 under a broken `Math.max` or `Math.min` (the screen read) and 402 under a broken `hasOwnProperty` or `Function.prototype.call` or a polluted `Object.prototype` (the text probe); 356 of them read more, 142 differ only in the calls made. The lab build differs on 33 of the 36 intact windows, in its timers and call order alone (the 200 ms fallback below): the readings, stored values and ids are the same. The stability harness gives the same ids in Chromium 153, Firefox 155 and WebKit 26.6 here. `ID_VERSION` stays 2.

**Client-hint brands (`x.ch.brands`, a hint).** The User-Agent Client Hints draft (WICG, 26 October 2026: 4.1.2 "create brands", 4.1.3 "create an arbitrary brand") has a browser add one brand made of words joined by characters from the list space, `(`, `)`, `-`, `.`, `/`, `:`, `;`, `=`, `?`, `_`, and does not require any particular word. A brand is left out when it holds one of those characters other than the space, or reads `NotABrand` once its spaces are removed; the word "not" alone decides nothing, and the version is never looked at, since the draft allows any. The unit tests enumerate the draft's algorithm itself: for lists of two to four words, every way of filling the gaps with the draft's characters, in the draft's order, and each character other than the space at either end of `Not A Brand`, as in the draft's own example `(Not;Browser`. Every form holding a character other than the space is dropped; of the forms joined by spaces alone only `Not A Brand` is, since nothing else tells such a form from a real name. Real names, a made-up one with the letters "not" among them included, are kept. The brands read on this PC on 13 November 2026 are in the tests as observations: Playwright's Chromium 153.0.8010.12 sent `HeadlessChrome`, `Not_A Brand` and `Chromium` headless, and `Chromium`, `Not_A Brand` with a window; Microsoft Edge 157.0.4341.46 and Google Chrome 157.0.8103.51 sent `Not-A.Brand`, their own name and `Chromium`. In each, exactly the arbitrary entry is dropped. The kept names are now sorted, decided in this change: the draft has browsers change the order over time (4.1.2), so the hint could move on a browser update while the set stayed the same; sorted, it stops changing with each release. Only the first 32 entries are read, so a list whose length is huge or infinite cannot hold the page; browsers send two or three. An entry that is not an object, or whose brand is not a string, is skipped instead of being written as text. The `no-brands` mark still counts every entry.

**System text style on WebKit (`x.txt.apple`).** Apple's notes for Safari 7.0 and WebKit's "Using the System Font in Web Content" (2015) give the Dynamic Type sizes to web content only through the system values of the `font` shorthand, such as `-apple-system-body`; `font-family: -apple-system` carries no size. WebKit's own test of this (`TextStyleFontSize.mm`) reads the computed size of that shorthand in a web view. The probe is unchanged in what it declares and reads, so the values are those of the build before it on every engine here. Measured on 13 November 2026: Chromium 153, Firefox 155 and Playwright's WebKit 26.6 Windows build all reject the declaration (the inline `font` reads back empty, `CSS.supports('font', '-apple-system-body')` is false), and the WebKit build reports the inherited 16 px, which is what `x.txt.apple` holds there. Reporting `!na` on a WebKit build that rejects it, and adding `-webkit-text-size-adjust: none` as WebKit's test does, would both move `p.txt`, so they wait for the single id-version change. Which acceptance check is true in Safari has to be measured on an iPhone first.

**Screen order (`x.scr`, `x.avail`).** CSSOM View (editor's draft, 5 November 2026, "Web-exposed screen information") defines `screen.width` and `height` as the web-exposed screen area and says nothing about rotation, and WebKit swaps the pair on some sites through a quirk (`Screen.cpp`, `QuirkTable.json`). So the order comes from the sizes alone, the longer first, with no other value consulted and no `Math` call. A side that is not a finite number above zero gives `!na`; before, an infinite side was written out. No browser reports one. In all three engines here an emulated 393x852 and 852x393 screen give `852x393`.

**Brave (`hw.mem`, `hw.cores`).** Excluded on every platform, on the basis of Brave's own documentation and our own measurements, not of any other project: Brave's wiki "Fingerprinting Protections" (edited 7 January 2026) and its farbling test page list hardware concurrency and device memory as altered in both Shields levels, brave-core (`navigator_base.cc`, `navigator_device_memory.cc`, issue 10808) randomises cores from 4 to the real count and memory from 4 to the real value per session and site, and our Pixel session saw both move (above). The page cannot see the Shields level, so the exclusion does not depend on it. Brave on desktop replaces the screen with a standard size tied to the window (brave-core `kBraveBlockScreenFingerprinting`, on by default on Windows, macOS and Linux); excluding the screen there would change ids, so it was listed for the id-version change. Id version 3 excludes it, after the window-resizing measurement on this PC (under "Id definition, version 3"). The language stays: Brave leaves `navigator.language` alone at the default level.

**Lab stage start and yield.** From the Cooperative Scheduling of Background Tasks draft (idle callbacks may be put off without limit during load, a timeout may be padded, a hidden page may get idle periods every 10 seconds) and the HTML Standard (timers clamp to 4 ms after five nested calls; a message port's queue is enabled by setting `onmessage`, and each message is its own task). The stage waits for three things in turn, each ended once by whichever of its signals comes first: `load` or 3 seconds; an idle callback with a 2-second timeout, or 2.5 seconds, or 200 ms where there is no idle callback; then a visible page, where only `hidden === true` counts as hidden. `go` runs once, the listeners are removed, and a listener or timer that cannot be set falls back to a timer. What changed from the build before: after the 3 seconds without `load`, an idle moment is still waited for, where the stage used to start at once; a `hidden` value that is not `true` no longer holds the stage; the start can no longer be asked for twice. Every turn given to the page is a message channel of its own, closed when its message arrives. Chromium 153 and Firefox 155 took the idle path here; Playwright's WebKit 26.6 has no `requestIdleCallback` and took the 200 ms timer, as every iPhone browser will. Not added: a backstop timer for a page whose `MessageChannel` never delivers (the 30-second watchdog answers there, and the timer would cost product bytes), and pausing the stage when the page is hidden part way (the share of lab readings ending in `!to` should show first whether it matters).

Cost: the five add 68 bytes to the gzipped product build, measured one file at a time against the build before: the brand filter, its sorting and its 32-entry bound about 83, closing each channel 14, the screen rule 4, while declaring the text probes' styles as pairs saved 33. In the same change the shorter banner saves 19 and the driver-name list, cut from 14 names to 8 ("Automation marks: sources" below), saves 42, so the build goes from 7,349 to 7,356 bytes.

## Rendering reads (lab build), 12 November 2026

The canvas, audio and Math reads were rewritten in `src/render.ts` from a behaviour specification (`research/specs/rendering-reads.md` in the workspace), itself written from the WHATWG HTML Standard's canvas chapter, the W3C Web Audio API 1.1 editor's draft, ECMA-262 section 21.3, `@mdn/browser-compat-data` and browser vendors' own documentation and bug trackers, all read on 12 November 2026. The values are new: nothing measured with the earlier reads (the phone figures above under "What stays out of both ids") carries over to them, and they have to be measured again on the phones. Nothing below is evidence for putting a rendering value into `id` or `idStrict`; these reads stay in the lab build and are meant for a later optional entry that tells desktop computers apart.

### Choices

| Question | Decision | Reason |
|---|---|---|
| What a canvas value hashes | The RGBA bytes from `getImageData`, not `toDataURL()` | The HTML Standard leaves the PNG encoder to the browser, so encoded bytes could change without the rendering changing, and encoding costs time |
| Digest | `short()`, the library's 64-bit digest, 16 hex digits, over a prefix with the key and size, then one character per byte | The supervisor's decision for the lab build. Every byte reaches the digest, so one changed byte changes the value (unit tests) |
| How often a canvas is read | Once. Each scene is drawn on two canvases, each read once, and the two are compared | Chromium with a GPU draws the text scene differently on a canvas after that canvas has been read back once (measured below), so a second read of one canvas reported noise that was not there on every load. Two drawings read once each still catch noise that changes per read, since two reads that each add their own noise differ |
| Canvas noise checks | Known cells in every read: a 16x16 pattern of 256 single-pixel cells in 256 colours, and a strip of two rows of cells above each scene, on both drawings and both readback variants, each checked byte for byte in the same `getImageData` result before anything is hashed; the two drawings of a scene carry different strips, and are then compared over the scene's own pixels, geometry first, then text | Mozilla documents a randomiser that alters 20 to 255 pixels per read and spares constant-colour canvases (Bugzilla 1887161): the pattern is all cells, so it cannot escape it. The pattern is read first, so an alteration of the first read only lands on it. The comparisons catch per-read noise, per-draw noise and rendering that is not reproducible. Until 13 November the pattern was the only check against an alteration that is the same on every read, so one that spared that single 16x16 read came out as values with the check `ok`; the strips closed that for any alteration that reaches a known cell. The third review then showed that an alteration keyed by contents that spares canvases of 16 colours or fewer (the pattern then had 16) and changes only 20 pixels missed both strips in about 29% of sessions, since the strips are about 3% of each scene canvas and two identical drawings got the same change. The pattern now has as many colours as pixels, and the differing strips make two drawings' contents differ, so such an alteration picks other pixels in each and the pair no longer matches (below, "What no check sees", and the measurements of 13 November) |
| A `SecurityError` from `getImageData` on our own canvas | `!noise`, `r.cchk` `blocked` | The specification's recommendation (its Q5): a browser that refuses readback on purpose gives no rendering evidence, and `!noise` keeps a later id from being built on it |
| Text scene | Generic families only; Arabic and three symbols kept for shaping and fallback; no emoji, Han, Kana, Hangul or Cyrillic | Named families would be font enumeration. Han glyphs follow the language. Arabic is the riskiest element and stays until readings decide (the specification's Q4); Chromium's UI language moves `r.ct` (measured below) |
| Strings drawn | Built from character codes | The minifier wrote the line of Greek and Arabic as raw UTF-8, so a page served in another encoding would have drawn other characters. A test checks that every build is ASCII |
| `willReadFrequently` | Both: `r.cg` and `r.ct` on default canvases, `r.cgcpu` and `r.ctcpu` on `willReadFrequently: true` canvases, each read once | Each costs one drawing and one read; the data chooses (the specification's Q3) |
| Giving the page a turn | The canvas read is a sequence of fifteen steps (`canvasSteps()`): the pattern, two geometry drawings, one step per text row that measures its string in its font, two text drawings, two digests and, in the lab build, two more drawings with their digests. The lab stage runs each step as a task of its own | As one task the read was a long task (over 50 ms) on a first view at 4x and 6x CPU slowdown, and a font's first use in a page is most of the text scene's cost there (timings below). `canvas()` still runs the whole sequence in one call for callers that want that |
| Released canvases | Each canvas is set to 0 by 0 once read | Frees the bitmaps of the eleven small canvases the lab build reads with, which matters on phones with little memory |
| Audio graph | Sawtooth 6,000 Hz, wave shaper with `4x` oversampling, peaking biquad, compressor inside its knee, gain 0.8, 5,120 frames at 44,100 Hz, factory methods and positional constructor | The Web Audio draft leaves band-limiting, the oversampling filters and the compressor knee to each browser; factory methods and the positional constructor work back to Chrome 53 (MDN compatibility data) |
| Channels into the merger | The gain node that feeds merger input 0 has `channelCount` 1 and `channelCountMode` `explicit`, set before it is connected | Safari 7 to 14.0 and iOS Safari 7 to 14.4 have only `webkitOfflineAudioContext` (`@mdn/browser-compat-data` 8.1.9, `api.OfflineAudioContext`), the one path that takes the prefixed constructor. WebKit's source before September 2020 (WebKit/WebKit at 8a462cb6, 19 August 2019, `Source/WebCore/Modules/webaudio/`, read 13 November 2026): `ChannelMergerNode::checkNumberOfChannelsForInput` sums the channel counts of all connected inputs and `process()` copies every channel of every input into the output one after another; `DynamicsCompressorNode` creates its output with `defaultNumberOfOutputChannels = 2`; `GainNode::checkNumberOfChannelsForInput` gives its output the channel count of its input; and `AudioNodeInput::numberOfChannels` returns the node's `channelCount` when the mode is `explicit`, else the largest count among its connections. So the merger there gets the compressor's two channels on input 0 and the known buffer on input 1, outputs three, and the two-channel destination keeps the compressor's two: the known-answer check would have reported `!noise` (`pattern`) on every load. With the gain explicitly mono, input 0 is one channel and the known buffer is channel 1 again. The setters exist there (`AudioNode::setChannelCount` accepts 1 to the context's maximum and `setChannelCountMode` accepts `explicit`; MDN gives both from Safari 7). Measured unchanged in Chromium and Firefox (below). Verified from vendor source and documentation only: no engine that old runs on this PC, so it stays on the roadmap's "Needs a device" list |
| Wave-shaper curve | `x(1.95 - 1.365x²)`, multiplications only | The supervisor's decision on the specification's Q8: the engine's maths library cannot reach the curve, so a switch of maths library (Firefox's fdlibm mode) cannot move `r.audio` through it |
| Audio value | The exact bits of channel 0's 5,120 samples, written as little-endian bytes explicitly; `r.arms` beside it | A sum discards most of the information. The explicit byte order lets a server recompute the digest from the numbers on any machine |
| Audio known-answer channel | 256 values with odd 24-bit significands spread over every binary exponent from 2^-1 to 2^-126, the smallest normal single-precision number, alternating in sign | All 256 earlier values sat near 0.5, where one single-precision step is 2^-24 (about 6e-8), so any absolute noise below about 3e-8 rounded back to the same value and passed. A value near 2^-126 changes under absolute noise down to about 1e-45, and any relative noise above half a step changes every value. Subnormals are left out because audio code commonly flushes them to zero. Unit tests: absolute noise of 1e-8, 2.9e-8, 1e-9, 1e-12, 1e-20 and 1e-30 on the 256 known frames, Gaussian noise with a standard deviation of 1e-9, relative noise of 1e-7, and 1e-9 on four samples are all `!noise` |
| Other audio checks | `copyFromChannel` against `getChannelData`; silent and non-finite output | Brave documents altering `getChannelData` and `copyFromChannel`; WebKit documents noise on every sample (webkit.org, Private Browsing 2.0) |
| Audio time limit | 1,000 ms from the call, no retry | Renders below take a few milliseconds of the page's time; a failed render is evidence and a retry would hide it. The limit now starts before the context is built, as the specification says |
| Math | 28 calls, each in its own `try`, joined with `String()`; lab only, proposed for no id. When no slot holds a number the value is `!na` (every function missing) or `!err` | The supervisor's decision on the specification's Q6: it separates engines and operating systems, which the reading already knows. A digest of statuses alone would look like a value and describe only the page |

### What no check sees

The canvas checks see an alteration wherever it changes a known cell, and wherever it changes the two drawings of a scene differently. One that does neither passes, and the altered value is reported as a value with `r.cchk` `ok`. These shapes are of that kind; none was found in a browser, and an extension or a future protection could take any of them:

- **Smooth areas only**: changes only pixels that have a neighbour of nearly the same colour. The third review (13 November) measured a ±1 colour-keyed offset on pixels with a neighbour within 8 in every channel, on every read: changed values with `r.cchk` `ok` on 45 of 45 loads in Chromium (software and GPU), Firefox (normal and private) and WebKit. No known cell has such a neighbour, which is what lets the cells meet the opposite shape (sparing pixels like their neighbours, as WebKit's source does). WebKit's source gives isolated pixels the widest noise bounds, and Chrome's unshipped Incognito sketch alters every pixel, so neither is of this shape.
- **Keyed by position, sparing the pattern and the top two rows of every read**: both drawings of a scene get the same change at the same places.
- **Keyed by colour, sparing every cell colour**: the same.
- **A choice of pixels that ignores the top two rows**, such as a hash of the scene region or of a sample that misses those rows: the differing strips then do not move it, and both drawings get the same change.
- **Recognising and reproducing the known cells.**

The audio read's equivalent: an alteration of channel 0 only that `copyFromChannel` returns too (measured 12 November, below). An alteration whose choice of pixels follows from a canvas's whole contents is no longer of this kind: since 13 November the two drawings' contents differ in their strips, so it picks different pixels in each and the pair differs, when it does not reach a cell first.

## Automation marks: none added in 1.0

13 November 2026, owner decision. 1.0 ships no automation-marks entry. The core's eight `flags.auto` marks are unchanged and their list stays closed for 1.0 (R21). The rule for shipping a mark (R24, applied by `verdict()` in `lab/mark-truth.mjs`): zero firings on clean launches and on configurations a person chose, the test extensions included; a gate in code to the versions measured clean; nothing logged, violated or reported under Trusted Types or a strict Content Security Policy; a small measured cost; and every population inside the gate measured. No set of candidates worth shipping meets it.

### Why each candidate is held back

- `own-value` fires for people. In review, four of five ordinary extension kinds that set values on the `navigator` object itself (a language switcher, a full-profile user-agent switcher that also sets `vendor`, a privacy extension, a hardware and screen spoofer) produced it on a clean launch of Chromium 153 with no driver. That is the documented, expected result: the harness itself now shows the false positive.
- `frame-window` writes nothing to the element it creates, so no Trusted Types sink is reached; but without the write to `srcdoc` it no longer observes the state it was written for. The lab now also records `frame-srcdoc`, an own `srcdoc` on a fresh element, read as a descriptor only, to see whether that state shows without a write. `frame-window` fired in none of 216 clean configurations inside its gate; `frame-srcdoc`, run on Chromium 153 only so far, in none of 24.
- `no-webdriver` has never been seen firing in a real browser; its state is made only in the fake window of `test/botlab.test.mjs`. It fired in none of 180 clean configurations inside its gate (Chromium 101 on; below 93 it cannot look).
- `app-version`, `plain-getter`, `ua-version`: person-caused, by the user-agent switchers and the privacy extension, on every rung of the ladder (22, 68 and 24 configurations).
- `plugins-type`: the first read of the plug-in list costs milliseconds at script start in headed Blink, and the plug-in emulator with the native list empty makes its state (18 configurations).

## The deep entry, 13 November 2026

`visitojs/deep` (`src/deep.ts`, `src/deepseal.ts`; `dist/deep.min.js`, global `VisitoDeep`) answers the owner's decision O4: a separate, optional id from the heavier reads, with noise detection and per-browser exclusions, that never changes `id` or `idStrict`. Its design is `research/designs/deep.md` in the workspace, with the supervisor's choices on its open points (workspace `ROADMAP.md`, R22). It is experimental: its values are not frozen, and `DEEP_VERSION` may change in a minor release.

**Until readings from many real computers are measured, how well the deep id tells computers apart is unknown: it may give one id to many machines of one model, browser and driver, and several ids to one machine.** Everything below was measured on one PC. One PC can show where the deep id moves on one machine; it cannot show that two machines differ.

**Since 13 November 2026 the deep entry reads only the geometry scene and the audio render, in every engine** ("The text scene leaves the deep id", at the end of this section). The measurements below that name `r.ct`, a `gecko` rule or a text step were taken before that change; the values of `r.cg` and `r.audio` in them still hold.

### Needs a device or CI

- **Separation**, the question this entry exists for: many desktops; pairs of PCs of one model; NVIDIA, AMD and Intel GPUs and their drivers; macOS on Intel and Apple Silicon; Linux. Nothing here measures it.
- **Stability over weeks**: browser, OS and driver updates; font and language-pack installs; dual-GPU laptops on battery and mains; moving a window between displays; remote-desktop sessions.
- **Safari on macOS 26**, normal and private, which decides the `webkit` rule.
- **Release Firefox** in real normal and private windows, including Firefox's own interface language and the per-site protection changes it receives through Remote Settings, which Playwright's build does not.
- **Real displays and system settings**: the Windows display scale and text size themselves, a HiDPI laptop docked to a 100% monitor, a Retina Mac with an external display, with Chromium, Chrome and Edge. Here the browsers' own preferences and switches stood in for them; Blink did not move under any of them, Firefox did and leaves `r.ct` out.

### The text scene leaves the deep id, 13 November 2026

Decision (owner, 13 November 2026): a value enters an id only where it has been measured stable, and stability beats separation.
