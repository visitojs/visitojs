# Contributing

Thank you for taking the time. This page says how to set up, what a change has to prove, and what we will not merge.

## What helps most

- **Measurements from real devices.** The ids were decided from a small phone session (see [docs/DECISIONS.md](docs/DECISIONS.md)). A reading from a device or an in-app browser that is not listed there is worth more than code. Open an issue with the reading and say which phone and app it came from.
- **Bugs with a reproduction.** A user agent that is parsed wrongly, a browser where a read throws, a page that the library slows down.
- **Corrections to the docs**, including the legal pointers.

## Setup

You need Node.js 24 and npm. The `devEngines` field in `package.json` makes npm stop with `EBADDEVENGINES` on any other Node version, because that is the only one the build and tests run on in CI. The range is widened (to `^24.0.0 || ^26.0.0`, say) once CI also runs on the newer line, or as soon as Dependabot's npm updates start failing with `EBADDEVENGINES`, which happens when Dependabot's own updater moves past Node 24.

```sh
npm ci --ignore-scripts
npm test
```

`npm test` builds everything and runs the unit tests. It must pass before and after your change.

### Browser harnesses

The harnesses in `lab/` run real browsers through the `playwright` package pinned in `package.json`. They use two container images so that every build and every browser runs without network access and with CPU and memory limits. The browser image must be the one that matches the pinned Playwright version:

```sh
docker build -f lab/containers/dev.Dockerfile -t visitojs-dev .
docker build -f lab/containers/browsers.Dockerfile -t visitojs-browsers lab/containers

lab/run.sh npm test                                        # the unit tests, inside the container
lab/run-browsers.sh node lab/fault-matrix.mjs chromium     # also: firefox, webkit
lab/run-browsers.sh node lab/stability.mjs chromium
lab/run-browsers.sh node lab/defer.mjs chromium
lab/run-browsers.sh node lab/engines.mjs chromium
lab/run-browsers.sh node lab/testpage/e2e.mjs chromium
lab/old-engines/run.sh                                     # Chrome 53 to 80, from old Selenium images pulled on first use; without Docker, in user namespaces
BUNDLE=dist/visito.lab.min.js lab/old-engines/run.sh       # the same on the lab build
BUNDLE=dist/visito.defer.min.js lab/old-engines/run.sh     # and on the deferred build, which the page starts
BUNDLE=dist/deep.min.js lab/old-engines/run.sh             # the deep entry, on its own page
```

Set `BUNDLE=dist/visito.lab.min.js` to run it on the lab build, or `BUNDLE=dist/visito.defer.min.js` on the deferred build, or `BUNDLE=dist/deep.min.js` on the deep entry. On the deferred build the page starts it, every fault in place before the script loads runs again installed between load and `start()`, and three more rows break the options or start it from a handler that throws. On the deep entry each `get()` call is answered once and after it returned, the reading is well formed with the id Node recomputes, and every rendering row gives the deep outcome stated for it |
| `deep-stability.mjs` | The deep id stays the same across reloads, new contexts in two launches, pixel ratios, page locales, Chromium's interface language (`ar`, `ja`, `zh-CN`, `ko`, `th`, `de`, headless and with `--headed`), forced colours and a dark scheme, and the display scale, text size and zoom a person sets, each written into a new profile (`scale-settings.mjs`), in every engine that reads; `r.ct` is `!ex`; the rule is the documented one in each engine and for a Brave-shaped navigator; injected noise and Firefox's protection settings give noise, and `+EfficientCanvasRandomization` gives the same id (a tripwire for a Gecko change); the core reading is the same with the deep entry on the page; no request leaves the page. `--exe` runs an installed Chromium-based browser with a temporary profile |
| `stability.mjs` | The ids stay the same across reloads, fresh storage, an app update and rotation, and the product build serves the second view from its cache. The deferred build gives the same ids in each scenario, in stored mode and with `store: false` |

The WebKit test build is not Safari, but the screen exclusion covers every WebKit browser at the Safari 17 level, because a test for Safari itself cannot be checked without a real iPhone and a wrong one would split one phone's ids (decision 5 in `docs/DECISIONS.md`). It compares the readings, the callbacks, what was stored, every call made on the window and the built-ins called; on intact built-ins any difference fails, and under a broken one each difference is named better, worse or both wrong against the intact reading. Where the reference itself throws, hangs or miscounts callbacks, that failure is the reference's, and the candidate fails the run only by adding a kind of failure. It exits 1 on an intact difference, a built-in only the candidate calls, or a worse run |

The truth for each mark in each context comes from how the harness started the browser (`mark-truth.mjs`), never from the reading. `node lab/marks.mjs clean`, `driven` and `cost` (the lab build's lap for the candidates, headed, on a navigated page), then `node lab/marks.mjs --table` prints the counts and verdicts `docs/DECISIONS.md` records |

Continuous integration builds and runs the unit tests on Linux for every push and pull request, then decides from the files the change touches what else it needs (`.github/scripts/ci-changes.mjs`). Documentation, the demo site (`demo/`), the brand files (`.github/brand/`) and images outside `src/`, `test/` and `lab/` count as documentation: the site's checks are `test/site.test.mjs`, which the unit job runs, and `demo.mjs`, which you run before you open the pull request. Unless the change is documentation only, it runs the unit tests on Windows too and the first six harnesses in all three engines, the fault matrix on the product, lab and deferred builds and the deep entry. When the change touches `src/`, the build configuration, the dependencies, the old-engines harness or the CI wiring, it also calls `old-engines.yml`, which runs `old-engines/run.sh` on the product, lab and deferred builds and the deep entry; that workflow can be started by hand as well. With the repository variable `CI_LINUX_RUNNER` set, the Linux jobs, the old engines included, run on that self-hosted runner, where `run.sh` runs the images without Docker; only the Windows job does not run. A last job, `CI result`, fails unless every job the change needed ran and passed, and it is the one check the branch rules require. A release runs every one of these jobs on the tagged commit before it publishes, whatever the last change touched ([RELEASING.md](RELEASING.md)). `marks.mjs` is not in it: its clean launches need installed browsers.

A third, `browser-drift.yml`, runs every Monday and by hand, on a pinned runner image (`ubuntu-24.04`). It runs `engines.mjs --evidence` in the newest builds a GitHub runner can install: Chromium, Chrome stable, beta, dev and canary, and Edge stable, beta and dev; the pinned Firefox, Mozilla's Firefox stable, beta and nightly, and the Firefox of the next Playwright package; and the WebKit of the pinned, the latest and the next Playwright package. Edge canary is left out: Microsoft publishes it for Linux only through its apt repository, and Playwright 1.63.0 has no Linux path for that channel. Every install step and every harness step has its own time limit, so a browser that hangs fails its own step and the steps after it still run. It checks two things the pull-request run does not:

- **Every engine test the answer reads.** The lab build records each feature test's result under `x.ev.*`. In each browser, every set the engine's answer reads must give exactly the marks in `evidence()` in `lab/engine-truth.mjs`: five of five for its own engine, none of the other two, the Android tests, its own Safari 17 or Firefox 143 set, and Brave. Three of five tests decide an engine, so one test can change in a release without changing an answer. This run catches that change first. Two of the expected marks come from Playwright, not from the browser: WebKit test 1 (`GestureEvent`), which Playwright defines in every WebKit page, and the emulated phone's `onorientationchange` in Chromium, which comes from the mobile emulation Playwright turns on. A change in either is a Playwright change, and the run cannot see WebKit itself change `GestureEvent`.
- **The private-window canary.** In Firefox with `browser.privatebrowsing.autostart` (the preference behind "Always use private browsing mode"), `navigator.storage.getDirectory()` must still be refused with `SecurityError`, and the lab build must still answer `x.private` true. It counts only where the session is shown to be private first: there `navigator.storage.persist()` must settle `false` at once, while in a normal window it waits for a permission answer. A normal Firefox window must also open the file system, which shows the private run differs at all. Only Playwright's own Firefox builds count (the pinned one and the next package's). In Mozilla's builds, which Playwright drives over WebDriver BiDi, the canary's lines are printed as `UNVERIFIED`, with what was seen and what was expected, and count neither as a pass nor as a failure. WebKit's default contexts are in memory, so there it must be refused with `UnknownError`.

What it costs is an estimate until it has run: about 25 to 30 billed Linux minutes a week, roughly 110 to 130 a month, most of it installing browsers. Replace this with the first run's billed time. A scheduled workflow runs only from the default branch.

### When the drift run fails

A red drift run opens no issue and does not page anyone. GitHub may email the person who last changed its `cron` line, depending on that person's notification settings. **The maintainer who cuts releases looks at the latest run every Monday and before every release** (`RELEASING.md`). The failing step names the browser, and each `FAIL` line names the browser, its channel and version, and the test.

1. **Run it again by hand** (Actions, Browser drift, Run workflow). A failure that does not repeat is noise. Note it and stop there.
2. **A `FAIL` that ends in "the context did not open", a launch error (including "the private browser started"), a step that timed out, or a failed install step** is a tooling failure, not drift. It usually means a download address moved or Playwright stopped supporting a channel. Fix the workflow; the library is not affected. The other checks of that browser are still printed and its raw report is still written, so read them before you rerun.
3. **`<set> test i of n, <name>, no longer holds` or `now holds`.** A browser release changed a feature the engine vote or a threshold reads. Nothing has changed for visitors yet, because the other tests still carry the vote. A beta or nightly gives one or two release cycles before the change reaches stable. Replace the test under the rules in `docs/DECISIONS.md` ("Engine detection"). Find another feature that meets the same conditions across the engine's whole range, from compat data first and then the vendor's release notes. Keep the set at five, and check that the new set gives the same answer for every version in range. Change `src/env.ts`, `TESTS` and `evidence()` in `lab/engine-truth.mjs` in one pull request, test first, and record the sources in `docs/DECISIONS.md`. If the replacement changes the answer for any real browser, the maintainer decides whether that is a correction or a change of id definition. Moving a threshold is a change of what an id is built from, so it raises `ID_VERSION`. Never edit the table to the new value to make the run green. That hides the drift the run exists to show. WebKit test 1 (`GestureEvent`) and the Chromium phone's `onorientationchange` come from Playwright, not the browser: a change there is a Playwright change, so look at the Playwright release before you replace a test.
4. **`getDirectory() is refused with SecurityError ...: "resolves"` in Firefox**, or `x.private` not true there, in a `FAIL` line, which only Playwright's own Firefox gives, and only after the session was shown to be private. The file system now opens in private windows, which Bugzilla 1975760 was landing. From that version on, the library's Gecko answer is a wrong `false` or a `null`, not evidence. Record the first Firefox version that resolves in `docs/DECISIONS.md`; for a nightly that is its version number, and stable follows about two releases later. Then propose the cap in an issue: Gecko at or above that version answers `'!na'`. How the check learns the Gecko version, and whether to cap it or stop checking Gecko, are the maintainer's decisions. **An `UNVERIFIED` line is never a record.** If only a `moz-` channel resolves while Playwright's own Firefox still refuses, confirm in a real private window by hand before recording a version.
   **`the session is private: storage.persist() is refused at once` failing** means the canary was not evidence this week: the lines under it are printed as `UNVERIFIED`. Playwright or Firefox changed how a context under the autostart preference behaves, or `persist()` itself changed in private browsing. Find which with the measurement in `docs/DECISIONS.md` ("Watched every week"), and fix the harness before you read the canary again. `storage.persist() waits for a permission answer in a normal window` failing is the same for the control.
5. **The same check failing in WebKit** (`UnknownError` expected, or `x.private` not true) means WebKit opened the file system to in-memory sessions. Private windows would then read as a wrong `false` in pinned builds (decision 3 under "The in-memory-session check" in `docs/DECISIONS.md`). Record it and propose the fix in an issue the same way.
6. **`getDirectory() opens in a normal window` failing** means Firefox changed a normal window, or the run's environment blocks storage. Investigate that before you read anything into the private result.

## Rules for a change

1. **Test first.** Write the test, see it fail for the right reason, then write the code. A pull request shows both.
2. **ES5 output.** The build is checked with `es-check es5`. The source is TypeScript compiled with `lib: ["ES5", "DOM"]`, so `Promise`, `Object.entries` and the like do not compile. The code may call `.then` on a promise a browser returns; it never constructs one.
3. **Never throw into the page.** Every read goes through `safe()` or a `try`. If you add a read, add its faults to the fault matrix.
4. **No network calls, no telemetry, no remote code.** The library sends nothing. This is not negotiable.
5. **A value enters an id only with evidence.** Show that it stays the same on one device across its browsers, and say what it costs in milliseconds on a real phone. Add the entry to `docs/DECISIONS.md`. A change to what an id is built from also raises `ID_VERSION`. A change to the deep entry's scenes, audio graph, constants, digest, parts, or to its rule table where it changes the answer for a real browser, raises `DEEP_VERSION` instead (`src/deepseal.ts`); the two versions never move together.
6. **Keep each entry under its budget**, in bytes gzipped at Node's default level. A test in `test/bundle.test.mjs` enforces each one. Anything no id or flag needs belongs in the lab build.

   | Entry | Budget | Why this number | At 1.0.0 |
   |---|---|---|---:|
   | `dist/visito.min.js`, the core | 8,192 | The published limit | 7,460 |
   | `dist/visito.defer.min.js`, the deferred build | 8,192, and at most 134 more than the core | 102 more than the core measured when it was added, plus 32 | 7,568, 108 more than the core |
   | `dist/deep.min.js`, the deep entry | 7,232 | 7,089 measured when it was added, plus about 2%: room for a fix, not for a new read without a decision | 6,402, without the text scene |
7. **No code from any other project**, whatever its license: not a function, a regular expression, a table of tests or a fixture. Ideas are free. Implement them from vendor documentation, specifications and your own measurements, and record those sources in `docs/DECISIONS.md`.
8. **An automation mark beyond the core's eight ships only when `verdict()` in `lab/mark-truth.mjs` says so**, on records from `lab/marks.mjs`: zero firings on clean launches and on configurations a person chose, the test extensions included, in every population inside the gate it would ship behind. Until then it is a lab-only hint under `x.bot.*`.

## Style

Match the file you are in: two spaces, single quotes, no semicolons, `function` expressions in the source (it compiles to ES5). Comments say why, in one line; the code says what. Test names are sentences that state the behaviour.

Commit subjects are imperative and under 72 characters. Explain the reason in the body when the diff does not.

The logo, icons and preview image come from the brand kit and live in `.github/brand/` and `demo/`. The V is the icon: never type a second V beside it.

## Pull requests

- One change per pull request.
- Say what you tested and on which browsers or devices.
- Do not include readings, user agents or any other data from real users. Synthetic values with the same shape are fine.

## Labels

Every issue and pull request gets a kind (`bug`, `enhancement`, `documentation`, `performance`, `security`, `measurement`, `dependencies`), and where it helps an `area:` (`core`, `defer`, `deep`, `match`, `lab`, `ci`, `site`) and a `browser:` (`chrome`, `safari`, `firefox`, `brave`, `in-app`, `old engines`). `status:` says where it stands: `needs triage` on a new report, then `needs reproduction`, `needs device`, `confirmed` or `blocked`. A change to what an id is built from is labelled `id definition`, because it raises `ID_VERSION` and is called out in the changelog. `good first issue` and `help wanted` mark work that is ready for someone new.

Questions and ideas start in [Discussions](https://github.com/visitojs/visitojs/discussions); an idea becomes an issue once it is clear what would be built and how it would be measured.
